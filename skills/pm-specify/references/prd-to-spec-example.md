# PRD→Spec 完整转化实例：用户注册功能

## PRD 原文（转化前）

> **功能需求：用户注册（FR-001）**
>
> 用户需要能够注册成为平台的新用户，以便后续使用核心功能。用户在注册页面填写基本信息，包括邮箱、密码、用户名。系统需要验证信息有效性，注册成功后自动登录并跳转到仪表盘。要求支持邮箱验证，防止垃圾注册。密码需要有一定强度。成功指标：新用户注册转化率 > 40%，注册完成时间 < 60 秒。

典型的简略 PRD——业务导向，但缺少边界、验收细节和可执行性。AI 直接实现很容易偏差。

---

## 翻译过程：六步操作

### 第 1 步：提取 Outcomes
从 PRD 拿走"用户需要注册" + "为了使用核心功能" → 转化为可观察的成果。

### 第 2 步：补边界
PRD 没说不做什么 → 主动补出 Out-of-Scope（社交登录、手机号注册、企业邀请、高级反垃圾、忘记密码、多语言等）。

### 第 3 步：写 Gherkin
PRD 的"验证有效性"太模糊 → 拆成具体场景：成功注册、邮箱已存在、密码强度不足、必填字段为空、确认密码不匹配、无效邮箱格式。

### 第 4 步：拆任务
PRD 的功能描述 → 4 个 Task Group（前端界面、表单验证、注册 API、边缘处理）+ 依赖关系。

### 第 5 步：写约束+决策
PRD 的"密码强度" → 具体规则（8 位 + 字母数字）；补充技术/安全/性能/UI 约束。

### 第 6 步：活文档
后续需求变化 → 先改 Spec，再让 AI 重新生成代码。

## 转化后的 Spec 文档

**文件路径**：`specs/001-user-registration/spec.md`

```markdown
# Spec: 用户注册功能 (FR-001)

## 1. 预期成果 (Outcomes)
- 新用户能够成功创建账号，并立即获得访问权限。
- 用户感受到简单、安全、专业的注册体验，愿意完成注册流程。
- 系统有效过滤无效/恶意注册，维护用户数据质量。

## 2. 范围边界 (Scope)

### In-Scope（本次包含）
- 注册表单页面（邮箱、密码、用户名、确认密码）
- 客户端与服务端表单验证
- 邮箱唯一性检查
- 基本密码强度验证
- 注册成功后自动登录并跳转到仪表盘
- 注册失败的错误提示与友好引导
- 基本速率限制（防止暴力注册）
- 注册成功后的欢迎邮件（可选，基础版）

### Out-of-Scope（本次明确排除）
- 社交登录（Google、Apple、微信等 OAuth）
- 手机号注册或国际手机号验证
- 企业/团队邀请注册
- 高级反垃圾（如 CAPTCHA、设备指纹）
- 邮箱验证链接点击确认（本次仅发送验证邮件，后续迭代）
- 忘记密码 / 账号恢复
- 多语言支持（本次仅中文 + 英文）

[NEEDS CLARIFICATION: 是否需要立即发送验证邮件并要求点击后才能登录？]

## 3. 约束与假设 (Constraints & Assumptions)
- 技术约束：使用现有技术栈（Next.js + Supabase）。不引入新外部认证服务。
- 安全约束：密码哈希存储，不得明文。符合 GDPR/CCPA 基本隐私要求。
- 性能约束：注册响应 < 2 秒，页面加载 < 1.5 秒。
- UI/UX 约束：遵循设计系统。移动端响应式。
- 假设：用户已有邮箱；平台面向个人用户；后端已有用户表基础结构。
- 非功能要求：可访问性（WCAG AA）、错误日志、监控注册成功/失败率。

## 4. 已做决策 (Decisions Made)
- 认证方式：邮箱 + 密码（后续可扩展）
- 用户唯一标识：邮箱作为主键
- 密码规则：至少 8 位，含字母 + 数字
- 成功后行为：自动登录 + 跳转 /dashboard

## 5. 任务拆分 (PM 粒度)

Task Group 1: 注册前端界面
- 1.1 创建 /register 路由和页面组件
- 1.2 实现响应式注册表单（字段 + 实时验证反馈）
- 1.3 错误提示与加载状态 UI

Task Group 2: 表单验证与业务逻辑
- 2.1 客户端验证（必填、格式、密码匹配）
- 2.2 服务端验证与唯一性检查
- 2.3 密码强度检查

Task Group 3: 注册 API 与数据处理
- 3.1 注册 API 端点（POST /api/auth/register）
- 3.2 用户数据创建与密码哈希
- 3.3 自动登录（生成 session/token）

Task Group 4: 边缘处理与集成
- 4.1 速率限制与安全头
- 4.2 注册成功邮件发送
- 4.3 跳转逻辑与欢迎体验

依赖关系：Task 1 → Task 2 → Task 3 → Task 4

## 6. 验收标准 (Gherkin 格式)

Feature: 用户注册

Scenario: 使用有效信息成功注册
Given 用户在注册页面
When 填写有效邮箱 test@example.com、密码 Pass1234、用户名"张三"，并点击"注册"
Then 显示成功提示"注册成功，欢迎加入"
And 自动登录
And 跳转到 /dashboard 页面

Scenario: 邮箱已存在注册失败
Given 用户在注册页面
When 使用已注册的邮箱 existing@example.com 填写其他信息并提交
Then 显示错误提示"该邮箱已被注册"
And 表单不提交成功

Scenario: 密码强度不足
Given 用户在注册页面
When 填写密码"123"（长度小于 8 位，缺少字母）
Then 实时显示密码强度提示"密码需至少 8 位，包含字母和数字"
And 提交时阻止注册并显示具体错误

Scenario: 必填字段为空
Given 用户在注册页面
When 邮箱为空，点击注册
Then 邮箱字段显示红色提示"此字段必填"
And 不提交表单

Scenario: 确认密码不匹配
Given 用户在注册页面
When 密码输入 Pass1234，确认密码输入 Pass5678
Then 显示错误"两次密码输入不一致"
And 阻止提交

Scenario: 无效邮箱格式
Given 用户在注册页面
When 输入"missing.com"作为邮箱
Then 提示"请输入有效的邮箱地址"

Edge Cases:
- 连续快速提交 5 次 → 速率限制触发，显示"操作太频繁，请稍后再试"
- 网络断开时点击注册 → 友好提示"网络连接失败，请检查网络后重试"并保留表单数据
- 移动端竖屏触屏操作 → 表单可正常填写和提交

## 7. 成功指标 & 监控
- 注册完成率 > 85%（从进入页面到成功）
- 注册失败主要原因分布（产品监控）
- 页面加载性能指标（LCP < 1.5s）

## PM 手动验证清单
1. 在无痕模式下完整走通注册流程
2. 检查所有错误场景提示是否友好
3. 验证新用户能立即使用核心功能
4. 确认 Out-of-Scope 的功能未被意外实现（如：不应出现 Google 登录按钮）
5. 移动端体验正常
```
