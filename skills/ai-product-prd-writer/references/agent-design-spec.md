# Agent 编排模式与设计模板 — PRD 写作参考

> 本文档为 AI 产品经理撰写 Agent 类产品 PRD 时的参考手册。聚焦于「PM 需要定义什么」而非「工程如何实现」。

---

## 一、六种核心编排模式

产品经理不需要选框架，但必须选**编排模式**——它决定了 Agent 之间的协作方式、故障边界和用户体验。

| # | 模式 | 一句话描述 | 适用场景 | PM 需定义的关键要素 |
|---|------|-----------|---------|-------------------|
| 1 | **Sequential Pipeline** | 线性流水线 A→B→C | 流程确定、步骤间强依赖 | 阶段拆分、各阶段 I/O Contract、超时策略 |
| 2 | **Parallel Fan-out/Gather** | 多维度并行处理后汇总 | 多角度分析、批量处理 | 并行维度、聚合逻辑、部分失败容忍度 |
| 3 | **Router/Dispatcher** | 入口路由到专家 Agent | 多意图入口、客服分流 | 路由规则（Intent Classification）、Fallback 路径、置信度阈值 |
| 4 | **Supervisor/Manager** | 复杂任务分解 + 协调 | 开放性任务、研究类需求 | 任务分解粒度、子任务边界、Escalation 规则 |
| 5 | **Hierarchical Delegation** | 多层级组织结构 | 企业级复杂流程 | 各层级职责、审批/汇报链、跨层通信规则 |
| 6 | **Generator-Critic (Debate)** | 生成 + 质量关卡迭代 | 内容生成、代码审查 | Review 维度、最大迭代次数、"足够好"标准 |

### 2026 年生产环境共识

- **Hub-and-spoke（Supervisor）是最主流模式**，适合大多数首次上线的 Agent 产品
- **起步建议 3-5 个 Agent**，超过 20 个 Agent 的系统在实际运行中表现持续低于预期
- 模式可组合：例如 Supervisor 内部某个子 Agent 使用 Generator-Critic 模式

### 模式选择决策树

```
任务流程是否确定？
├── 是 → 步骤间有并行可能？
│   ├── 是 → Parallel Fan-out/Gather
│   └── 否 → Sequential Pipeline
└── 否 → 入口意图是否多样？
    ├── 是 → Router/Dispatcher（前端） + Supervisor（后端）
    └── 否 → 任务复杂度？
        ├── 单层可解 → Supervisor/Manager
        ├── 需多层级 → Hierarchical Delegation
        └── 需质量迭代 → Generator-Critic
```

## 二、Agent Story 格式

传统 User Story 不够用——Agent 产品需要同时定义「Agent 做什么」和「做不好时怎么办」。

### 模板

```
As [Agent 角色名],
Given [输入上下文 + 可用工具列表],
When [触发条件],
Then [预期输出 + 质量标准],
Fallback [失败时的降级行为],
Boundary [此 Agent 绝对不能做的事]
```

### 示例：简历优化 Agent

```
As 简历优化 Agent,
Given [用户简历文本 + 目标 JD + 行业知识库访问权限],
When [用户提交「优化简历」请求],
Then [输出优化后简历，匹配度评分 ≥ 80，修改点逐条标注],
Fallback [若 JD 解析失败，退回通用优化模式并提示用户],
Boundary [不编造工作经历，不删除用户未授权删除的内容]
```

## 三、Context / Memory 三层模型

基于 Google ADK 的三层架构，PM 需要在 PRD 中明确每层的范围和生命周期。

| 层级 | 名称 | 生命周期 | PM 需定义 | 示例 |
|------|------|---------|----------|------|
| L1 | **Session State** | 当前会话 | 哪些信息在会话内共享、会话超时时间 | 当前对话的用户意图、已完成步骤 |
| L2 | **Artifact Store** | 跨会话持久化 | 存什么、存多久、谁能访问 | 用户上传的文件、生成的报告（通过引用传递，不塞进 Prompt） |
| L3 | **Memory Layer** | 长期知识 | 记忆范围、遗忘策略、隐私边界 | 用户偏好、历史交互摘要、学到的领域知识 |

### PRD 中的 Context 设计 Checklist

- [ ] 每个 Agent 能看到哪些 Context？（最小权限原则）
- [ ] 大文件/数据资产是否通过 Artifact Store 引用传递？（避免 Token 浪费）
- [ ] 跨会话记忆是否需要用户确认/可删除？（隐私合规）
- [ ] Session 超时后 Context 如何处理？（清除 vs 摘要保留）

## 四、PM 定义 vs 工程决策：职责边界

写 PRD 时最常见的问题：写多了越界，写少了留坑。以下是明确的分界线。

| PM 必须定义（写进 PRD） | 工程决策（不写进 PRD） |
|------------------------|---------------------|
| Agent 角色与职责边界 | Framework 选型（LangGraph / CrewAI / ADK） |
| 协作模式（上述六种之一或组合） | State 持久化方案（Redis / DB） |
| 任务分解逻辑与粒度 | Token 优化策略 |
| 成功标准（可量化） | 并发控制实现 |
| Human-in-the-loop 触发条件 | Observability 埋点方案 |
| 错误处理与 Fallback 行为 | 重试机制与熔断实现 |
| Context 共享范围与隐私要求 | 消息队列选型 |

## 五、PRD Agent 设计章节模板

以下模板可直接嵌入 PRD 的「系统设计」或「技术方案」章节。

### 5.1 Agent 角色定义表

| Agent 名称 | 职责描述 | 输入 | 输出 | 可用工具 | 约束 |
|-----------|---------|------|------|---------|------|
| `{agent_name}` | `{一句话职责}` | `{输入数据格式}` | `{输出数据格式 + 质量标准}` | `{API/DB/搜索等}` | `{不能做什么}` |
| ... | ... | ... | ... | ... | ... |

### 5.2 编排模式声明

```
编排模式：{模式名称}
选择理由：{为什么选这个模式}
Agent 数量：{N} 个
协作拓扑：{文字描述或 Mermaid 图}
```

### 5.3 任务流转规则

```
触发条件：{用户操作 / 系统事件 / 定时触发}
入口 Agent：{名称}
流转规则：
  - {条件A} → {Agent X}
  - {条件B} → {Agent Y}
  - {无法分类} → {Fallback 处理}
终止条件：{什么时候任务算完成}
超时策略：{单步超时 N 秒 / 总超时 M 秒 / 超时后行为}
```

### 5.4 Human-in-the-loop 设计

| 触发条件 | 人工介入方式 | 超时处理 |
|---------|------------|---------|
| `{置信度 < X%}` | `{推送审批 / 弹窗确认}` | `{自动降级 / 挂起等待}` |
| `{涉及资金 > Y 元}` | `{强制人工审批}` | `{拒绝执行}` |
| `{迭代次数 > N}` | `{展示结果让用户选择}` | `{输出当前最优结果}` |

### 5.5 错误处理与降级

| 故障场景 | 影响范围 | 降级策略 | 用户感知 |
|---------|---------|---------|---------|
| `{单个 Agent 超时}` | `{该子任务}` | `{跳过/重试/人工接管}` | `{提示文案}` |
| `{LLM API 不可用}` | `{全局}` | `{缓存结果/规则兜底}` | `{提示文案}` |
| `{Context 溢出}` | `{当前 Agent}` | `{摘要压缩/分段处理}` | `{无感/轻提示}` |

## 六、Anthropic 的关键洞察（来自 Building Effective Agents）

三条写 PRD 时最容易忽略的点：

1. **Task Boundary 必须清晰** — 每个 Agent 的职责边界要写到「不能做什么」级别，模糊边界是多 Agent 系统最大的 bug 来源
2. **Effort Scaling 规则要嵌入 Prompt** — Agent 需要知道什么时候该深入、什么时候该快速给出结果；PM 要定义这个判断标准，而不是让 Agent 自己猜
3. **Observability 是多 Agent 系统的生命线** — PRD 中必须包含「我们如何知道每个 Agent 在做什么」的可观测性要求，否则上线后无法调试

## 七、快速参考卡片

```
写 Agent PRD 的 5 个必答题：

1. 用几个 Agent？各自做什么、不做什么？
2. 它们之间怎么协作？（选编排模式）
3. 什么时候需要人介入？
4. 出错了怎么办？（每个故障场景）
5. 怎么知道系统在正常工作？（可观测性要求）
```
