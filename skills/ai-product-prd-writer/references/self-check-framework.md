# AI 产品 PRD 自检框架

> 本文件定义了 AI 产品 PRD 的结构化质量检查维度。在 PRD 全部模块生成完毕后，按以下框架逐维度审查，输出自检报告。
>
> 设计参考：check-prd skill 的 14 维度审查结构，针对 AI 产品 PRD 做了专项适配。

---

## 自检前准备

1. 确认 PRD 的产品类型（工具型 / Agent 型 / 对话型 / 平台型）
2. 确认需求规模（小需求 / 中等 / 完整产品）
3. 根据类型和规模，标记不适用的维度

### 适用性规则

| 维度 | 适用条件 | 不适用时处理 |
|------|---------|------------|
| D5 Agent 设计 | 仅 Agent 型/平台型产品 | 标注"不适用" |
| D6 Prompt 规范 | 所有涉及 LLM 调用的产品 | 不涉及 LLM 则标注"不适用" |
| D7 评估体系 | 中等及以上规模 | 小需求标注"本期跳过" |
| D9 埋点与运营 | 中等及以上规模 | 小需求标注"本期跳过" |

---

## 输出格式

### 每个维度的输出

```md
## 维度 D[编号] - [名称] ｜ 评级：[优秀 / 合格 / 待改进 / 严重缺失]

### 具体发现

**发现 1：[问题标题]** [P0/P1/P2/P3]
- PRD 定位：第 X 模块 / [功能名称]
- 问题描述：[具体说明问题]
- 改进示例：[给出可以立刻执行的改法]

### 隐性问题推断
结合产品类型和业务场景，列出 PRD 没写但按道理必须考虑的问题。
```

### 优先级说明

本文件中的 P0-P3 指**问题严重度**（P0=必须修复，P1=上线前修订，P2=可改进，P3=优化建议），与 module-specs.md 中功能规划的 P0-P3（功能优先级：价值×成本矩阵）含义不同，注意区分语境。

### 最低质量标准

- 每个维度至少 3 条具体发现，或 3 条"为何没有问题"的明确说明
- 发现必须锚定到 PRD 中的真实模块、流程或字段
- 建议必须可执行，不得笼统模糊

## 检查维度（10 个）

### 阶段 1：业务与定位

#### D1 业务背景与目标质量

**检查清单**：

- [ ] **Why & Why Now 是否有说服力**
  - 优质标准：30 秒内能让读者理解问题是什么、为什么重要、为什么现在做
  - 问题标志：开头是"随着 AI 技术的发展..."等空话，无具体数据和场景
  - 改进方向：补充具体数据（耗时、成本、错误率），用"现状→痛点→机会点"三列表格

- [ ] **目标是否可量化**
  - 优质标准：北极星指标 + 商业/业务/技术指标均有明确数值和度量方式
  - 问题标志：出现"提升用户体验"、"提高效率"等无法衡量的目标
  - 改进方向：每个目标必须有指标名、目标值、度量方法、数据来源

- [ ] **用户画像是否真实**
  - 优质标准：有角色名称、专业背景、核心任务、痛点、诉求，痛点与背景对应
  - 问题标志：用户画像是"所有用户"、痛点是编造的、与前面的业务背景脱节
  - 改进方向：用角色卡片形式，描述真实使用场景

- [ ] **基础信息是否完整**（对应模块一）
  - 优质标准：版本号、创建时间/人、变更日志表格齐全；名词解释覆盖所有 AI 术语和业务专有名词
  - 问题标志：无版本号、无变更记录、AI 术语（RAG/Agent/Embedding 等）未在名词解释中定义
  - 改进方向：补充名词解释表，确保非 AI 背景的读者也能理解文档

#### D2 产品定义与竞品分析

**检查清单**：

- [ ] **产品定位是否清晰**
  - 优质标准：能用一句话说清"为谁、解决什么问题、用什么方式、区别于谁"
  - 问题标志：读完 PRD 仍无法概括产品是什么

- [ ] **竞品分析是否有洞察**
  - 优质标准：至少分析 2-3 个竞品，重点是"我们可以借鉴什么"和"我们的差异化在哪"
  - 问题标志：只列竞品名称和功能列表，无分析深度

- [ ] **AI 能力范围是否明确**
  - 优质标准：明确了核心 AI 技术（RAG/Agent/多模态等）、使用模型、外部集成、多 Agent 协作情况
  - 问题标志：只写了"使用 AI 技术"，不说具体用什么

---

### 阶段 2：功能与流程

#### D3 功能规划完整性

**检查清单**：

- [ ] **功能清单是否有优先级**
  - 优质标准：每个功能有优先级标注（P0-P3 或 MoSCoW）、一句话验收标准
  - 问题标志：功能列表无优先级，或全部标为 P0

- [ ] **范围边界是否清晰**
  - 优质标准：明确写了"不做什么"（Won't Have / P3），防止需求蔓延
  - 问题标志：只写了做什么，不写不做什么

- [ ] **功能是否构成闭环**
  - 优质标准：沿核心流程走查，每个环节都有功能支撑
  - 问题标志：存在"创建了但无法查询"、"生成了但无法编辑"等功能断点

- [ ] **详细交互是否可执行**（对应模块六）
  - 优质标准：每个核心功能有入口、交互步骤、系统反馈（加载/成功/失败）、异常处理
  - 问题标志：只列了功能名称，开发不看完还要来问"用户从哪进来"、"失败了显示什么"
  - 改进方向：按功能逐个补全入口→交互→反馈→异常四要素

- [ ] **角色权限是否定义**（对应模块十二）
  - 优质标准：权限矩阵表（行=功能，列=角色），标注谁可改 Prompt、查看评估数据、标注训练数据
  - 问题标志：多角色产品但无权限区分，或 AI 管理类操作（Prompt 编辑、数据标注）无权限控制
  - 改进方向：补充权限矩阵，AI 管理权限单独列出

#### D4 流程设计质量

**检查清单**：

- [ ] **是否有流程图**
  - 优质标准：用户操作流程 + 系统处理流程均使用 Mermaid 代码块
  - 问题标志：纯文字描述流程，无可视化

- [ ] **是否覆盖异常路径**
  - 优质标准：流程图包含正常路径 + 异常分支 + 边界条件
  - 问题标志：只有 Happy Path，未考虑失败、超时、数据异常等情况

- [ ] **人机协作边界是否清晰**
  - 优质标准：明确了哪些步骤由 AI 完成、哪些需要人工确认、哪些人工不可绕过
  - 问题标志：AI 自动做出关键决策但用户无法干预

### 阶段 3：AI 专项设计

#### D5 Agent 设计质量（Agent 型/平台型适用）

**检查清单**：

- [ ] **Agent 角色边界是否清晰**
  - 优质标准：每个 Agent 用 Agent Story 定义（As/Given/When/Then/Fallback/Boundary），Boundary 字段明确"不做什么"
  - 问题标志：Agent 职责模糊，多个 Agent 有重叠，或边界未定义
  - 参考：agent-design-spec.md

- [ ] **编排模式是否合理**
  - 优质标准：明确选择了编排模式（Sequential/Parallel/Router/Supervisor 等），并说明选择理由
  - 问题标志：多 Agent 但无协作模式定义，或 Agent 数量 > 10 但未分层

- [ ] **Context/Memory 管理是否完整**
  - 优质标准：定义了全局上下文结构、Agent 间信息传递方式、会话状态管理
  - 问题标志：多 Agent 协作但无 Context 管理方案，信息如何在 Agent 间流转不清楚

- [ ] **Human-in-the-loop 是否定义**
  - 优质标准：明确了什么条件需要人工介入、介入方式、超时处理
  - 问题标志：全自动无任何人工干预点，或关键决策由 Agent 独立完成

#### D6 Prompt 设计质量（涉及 LLM 的产品适用）

**检查清单**：

- [ ] **Prompt 结构是否完整**
  - 优质标准：覆盖 10 节核心结构（元信息→System Prompt→Input→Output→Few-shot→Guardrails→Multi-turn→Tool Calling→评估标准→版本管理），可根据场景裁剪
  - 问题标志：只有 System Prompt 的 Role 部分，缺少 Output 格式、Constraints、Few-shot
  - 参考：prompt-design-spec.md

- [ ] **输入输出规范是否明确**
  - 优质标准：Input Schema 有变量名、类型、必填/选填；Output Schema 有 JSON 结构定义
  - 问题标志：只写了"用户输入问题，AI 返回结果"，无具体 Schema

- [ ] **Guardrails 是否分层设计**
  - 优质标准：覆盖 Input 层（注入检测、PII 过滤）→ Model 层（Constraints）→ Output 层（内容审核、Schema 校验）
  - 问题标志：无任何安全防护，或只在 System Prompt 中加了一句"不要输出有害内容"

- [ ] **Edge Cases 是否覆盖**
  - 优质标准：定义了输入为空、输入超长、对抗性输入、模型不确定时的处理方式
  - 问题标志：只考虑正常输入场景

- [ ] **槽位设计是否完整**（对话型产品适用）
  - 优质标准：定义了槽位名、必填/选填、数据类型、提取方式、追问话术、验证规则
  - 问题标志：对话型产品需要收集多参数但无槽位设计

#### D7 评估体系质量

**检查清单**：

- [ ] **是否覆盖 L1-L4 四层**
  - 优质标准：L1 连通性 + L2 准确性 + L3 业务影响 + L4 持续改善，每层有具体指标和目标值
  - 问题标志：只写了"准确率 ≥ 90%"，未分层

- [ ] **Benchmark 测试集是否定义**
  - 优质标准：≥ 10 条测试用例，覆盖 Happy Path / Edge / Adversarial / Drift 四类
  - 问题标志：无测试集，或只有 3-5 条全是正常场景

- [ ] **评估执行方式是否明确**
  - 优质标准：定义了三级评估（自动化 → LLM-as-Judge → 人工）的执行频率和职责
  - 问题标志：只写了指标但不说怎么测、谁来测、多久测一次

- [ ] **Badcase 闭环是否定义**
  - 优质标准：有 发现→归因→修复→验证→沉淀 的完整流程，含响应 SLA
  - 问题标志：无 Badcase 处理流程，或只说"持续优化"
  - 参考：evaluation-framework.md

### 阶段 4：健壮性与运营

#### D8 兜底策略与异常处理

**检查清单**：

- [ ] **兜底场景是否全面**
  - 优质标准：覆盖检索失败、AI 超时、模型不可用、输入超出能力范围、敏感内容等
  - 问题标志：只写了"AI 超时返回错误提示"，未覆盖其他场景

- [ ] **每个兜底是否有三要素**
  - 优质标准：触发条件 + 系统行为 + 用户感知，三列表格
  - 问题标志：只写了触发条件但不说系统怎么处理、用户看到什么

- [ ] **核心流程是否有非 AI 回退**
  - 优质标准：AI 完全不可用时，用户仍能通过规则引擎或手动操作完成核心业务
  - 问题标志：核心业务流程完全依赖 AI，AI 宕机 = 业务中断

#### D9 埋点与运营设计

**检查清单**：

- [ ] **AI 专项埋点是否定义**
  - 优质标准：包含模型调用次数、平均响应时间、兜底触发次数、用户采纳率（thumbs up/down）
  - 问题标志：只有页面 PV/UV，无 AI 能力维度的埋点

- [ ] **用户反馈闭环是否设计**
  - 优质标准：用户可对 AI 输出进行反馈（采纳/丢弃/重新生成），反馈数据回流到评估体系
  - 问题标志：AI 输出后无任何反馈机制，无法知道用户是否满意

#### D10 非功能需求与可观测性

**检查清单**：

- [ ] **性能指标是否量化**
  - 优质标准：TTFB、完整响应时间、并发量均有目标值和测量方法
  - 问题标志：只写了"响应要快"，无具体数值

- [ ] **安全与合规是否覆盖**
  - 优质标准：数据脱敏、PII 处理、审计日志、内容安全、合规要求均有定义
  - 问题标志：将用户数据直接传给第三方 LLM API 而无脱敏措施

- [ ] **可观测性是否独立定义**
  - 优质标准：日志记录（范围+保留时长）、指标监控（阈值+告警）、错误追踪（分类+SLA）、链路追踪（Agent 决策链路可追溯）
  - 问题标志：无任何监控设计，上线后无法知道系统状态

- [ ] **外部系统集成是否明确**
  - 优质标准：每个外部系统有集成类型、用途、认证方式、频率限制、降级策略
  - 问题标志：只写了"调用 XX API"，未定义降级和限频

## 重大风险项清单（AI 产品特有）

以下任一项存在，建议在评审时重点讨论。

| 编号 | 风险项 | 触发条件 | 为什么重要 |
|------|--------|---------|----------|
| R1 | **无兜底策略** | PRD 未定义 AI 不可用时的回退方案 | AI 宕机 = 业务中断 |
| R2 | **无评估体系** | PRD 无 Benchmark、无质量指标、无测试集 | 上线后无法判断 AI 效果 |
| R3 | **Prompt 无 Guardrails** | 未定义注入检测、内容审核、PII 过滤 | 安全漏洞，可能泄露数据或输出有害内容 |
| R4 | **Agent 无边界定义** | 多 Agent 但无 Boundary 定义 | Agent 职责重叠或遗漏 |
| R5 | **核心流程完全依赖 AI** | 无非 AI 回退路径 | 单点故障风险 |
| R6 | **敏感数据未脱敏** | 将 PII/商业机密直接传给第三方 LLM | 合规风险 |
| R7 | **无可观测性设计** | 多 Agent 系统无链路追踪 | 上线后无法调试 |

## 快速自检流程

时间有限时，按以下顺序快速扫描：

1. **重大风险项扫描**（R1-R7）——有触发的项直接标为 P0
2. **D8 兜底策略** + **D7 评估体系**——AI 产品最常缺失的两个模块
3. **D6 Prompt 规范**——检查 Guardrails 和 Edge Cases
4. **D5 Agent 设计**——检查 Boundary 和 Context 管理
5. **其余维度**——按 D1-D4, D9-D10 顺序扫描
