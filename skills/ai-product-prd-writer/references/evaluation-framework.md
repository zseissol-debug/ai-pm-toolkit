# AI 产品评估体系与 Badcase 迭代指南

> 本文件为 PRD 撰写 skill 的参考资料，提供评估指标选取、Benchmark 设计、评估分层执行和 Badcase 闭环迭代的实操框架。

---

## 一、四层评估框架（L1-L4）

PRD 中的评估指标不应只写"准确率"，而应按层级递进覆盖：

| 层级 | 关注点 | 核心指标 | PRD 写法示例 |
|------|--------|----------|-------------|
| **L1 连通性** | 系统能不能跑通 | API 成功率、P95 延迟、错误率 | "TTFB < `[具体值，如2s]`，可用性 > `[如99.5%]`" |
| **L2 准确性** | 回答对不对 | Faithfulness ≥ 0.85、幻觉率 < 5%、Answer Relevancy ≥ 0.8 | "Golden Set 通过率 ≥ `[如90%]`" |
| **L3 业务影响** | 用户买不买账 | 采纳率、任务完成率、效率提升 | "AI 建议采纳率 ≥ `[如60%]`" |
| **L4 持续改善** | 能不能持续迭代 | 周评估频次、Canary/A-B 覆盖、Drift 检测 | "每周采样 `[0.5-1%]` 线上数据" |

**使用原则：**
- L1-L2 是上线门槛，必须在 PRD 验收标准中明确写出
- L3 是业务价值证明，写在成功指标（Success Metrics）中
- L4 是持续运营要求，写在运营方案或后续迭代章节中

## 二、主流评估框架速查

### 2.1 RAGAS

最常用的 RAG 评估框架，四维打分，均为 0-1 区间：

| 维度 | 含义 | 适用场景 |
|------|------|----------|
| Faithfulness | 回答是否忠于检索上下文 | 幻觉检测 |
| Answer Relevancy | 回答与问题的相关性 | 答非所问检测 |
| Context Precision | 检索结果中相关内容的排序质量 | 检索排序优化 |
| Context Recall | 检索结果对真实答案的覆盖度 | 检索召回优化 |

### 2.2 DeepEval

提供 50+ 指标，尤其适合 Agent 类产品。Agent 评估采用三层结构：

| 层级 | 指标 | 说明 |
|------|------|------|
| **Reasoning 推理层** | Plan Quality, Plan Adherence | 规划质量与执行一致性 |
| **Action 动作层** | Tool Correctness, Argument Correctness | 工具选择与参数准确性 |
| **Execution 执行层** | Task Completion, Step Efficiency | 任务完成度与步骤效率 |

### 2.3 ARES

与 RAGAS 相同三维度，但使用合成数据 + 微调 LM 做 Judge，仅需约 100 条人工标注即可启动，适合标注资源有限的团队。

**选型建议：**
- RAG 产品首选 RAGAS，生态成熟
- Agent/多步骤产品用 DeepEval 的三层框架
- 标注资源紧张时考虑 ARES 的合成数据路线

## 三、实用阈值参考

| 指标 | 内部工具 | 客户侧产品 | 高风险领域（医疗/金融） |
|------|----------|-----------|----------------------|
| Faithfulness | ≥ 0.7 | ≥ 0.85 | ≥ 0.95 |
| Context Precision | ≥ 0.7 | ≥ 0.85 | ≥ 0.9 |
| Answer Relevancy | ≥ 0.7 | ≥ 0.8 | ≥ 0.9 |
| 幻觉率 | < 8% | < 5% | < 1.5% |

**PRD 写法模板：**

```
验收标准：
- Faithfulness ≥ [具体值] （基于 [RAGAS/DeepEval] 框架评估）
- 幻觉率 < [具体值]%（基于 Golden Set [数量] 条测试用例）
- 答案相关性 ≥ [具体值]
- Golden Set 整体通过率 ≥ [具体值]%
```

## 四、Benchmark 设计（Golden Dataset）

### 4.1 用例分布

不要全是 Happy Path，按以下比例覆盖：

| 类型 | 占比 | 说明 | 示例 |
|------|------|------|------|
| Happy Path | ~40% | 典型正常场景 | 标准查询、常规操作 |
| Edge Cases | ~25% | 边界条件 | 超长输入、空值、极端参数 |
| Adversarial | ~20% | 对抗/注入场景 | Prompt injection、角色越权 |
| Distribution Shift | ~15% | 分布外样本 | 新领域数据、罕见表述方式 |

### 4.2 规模参考

| 阶段 | 建议条数 | 说明 |
|------|---------|------|
| Cold Start（冷启动） | 10-20 | 快速验证基本可行性 |
| Iteration（迭代期） | 20-50 | 覆盖已知问题类型 |
| Mature（成熟期） | 50-200 | 稳定回归基线 |
| Major Validation（大版本验证） | 200-1000 | 全面评估，含人工评审 |

**核心原则：Quality > Quantity。20 条来自真实失败案例的用例 > 200 条随机构造的用例。**

### 4.3 Golden Set 最低要求

- 最少 100 条高质量标注样本
- 每条需包含：输入、期望输出、评分维度、标注者、标注时间
- 定期清洗：剔除过时、歧义、重复用例

### 4.4 Benchmark 测试用例模板

| 字段 | 说明 | 示例 |
|------|------|------|
| `case_id` | 唯一编号 | `TC-RAG-042` |
| `category` | 用例类型 | Happy Path / Edge / Adversarial / Drift |
| `input` | 用户输入 | `"[用户问题原文]"` |
| `context` | 检索上下文（如适用） | `"[召回的文档片段]"` |
| `expected_output` | 期望回答 / 关键要点 | `"[标准答案或必须包含的要点]"` |
| `eval_dimensions` | 评估维度 | Faithfulness, Relevancy, 格式合规 |
| `pass_criteria` | 通过条件 | `"Faithfulness ≥ 0.85 且无幻觉"` |
| `source` | 用例来源 | 线上 Badcase / 人工构造 / 用户反馈 |
| `annotator` | 标注人 | `[姓名]` |
| `created_at` | 创建时间 | `[YYYY-MM-DD]` |
| `last_verified` | 最近验证时间 | `[YYYY-MM-DD]` |

## 五、三级评估执行体系

### 5.1 Deterministic Checks（确定性校验）

- **内容：** 格式校验、Schema 合规、长度限制、必填字段
- **频率：** 每次 CI 触发
- **工具：** 正则、JSON Schema、自定义校验脚本
- **成本：** 极低，全自动

### 5.2 LLM-as-a-Judge（模型评审）

- **内容：** 主观质量评估（连贯性、专业性、完整性）
- **频率：** 日常迭代主力，每次 Prompt 变更后运行
- **关键实践：**
  - 用更强的模型做 Judge（如用 Claude Opus 评审 Sonnet 输出）
  - 写清晰的评分 Rubric，每个维度 1-5 分，附具体描述
  - 消除位置偏差（随机化候选排序）和冗长偏差（控制评分 Prompt）
  - 低 Temperature（≤ 0.1）保证一致性

**Rubric 模板示例：**

```
维度：[如 Faithfulness]
5分：完全忠于上下文，零幻觉，引用准确
4分：基本忠于上下文，有微小推理但不影响结论
3分：大部分忠于上下文，但有1处明显超出上下文的断言
2分：多处脱离上下文，存在臆造信息
1分：回答与上下文无关或严重矛盾
```

### 5.3 Human Evaluation（人工评审）

- **内容：** Ground-truth 校准、高风险决策复核
- **频率：** 每 2-4 周一次
- **适用：** 新领域上线前、阈值调整、评估维度新增时

## 六、回归测试与线上监控

| 环节 | 做法 | PRD 中怎么写 |
|------|------|-------------|
| 版本管理 | Prompt、数据集、Grader 全部版本化 | "评估基础设施需支持 Prompt 版本化与评估结果追溯" |
| Golden Set 回归 | 固定 50-200 条，每次变更必跑 | "每次 Prompt 变更后自动触发 Golden Set 回归" |
| CI/CD 集成 | Prompt 变更自动触发评估 Pipeline | "评估 Pipeline 接入 CI/CD，阻断低于阈值的变更" |
| 线上 Drift 检测 | 定期采样 0.1% 流量 | "每 `[周期]` 采样 `[比例]` 线上请求进行离线评估" |

## 七、Badcase 闭环迭代流程

```
发现 → 归因 → 修复 → 验证 → 沉淀
```

### 各环节详解

| 环节 | 输入 | 动作 | 输出 |
|------|------|------|------|
| **发现** | 线上采样、用户反馈、评估跑批 | 标记问题样本，分配优先级 | Badcase 清单 |
| **归因** | Badcase 清单 | 分类问题类型（幻觉/遗漏/格式/检索失败/推理错误） | 问题归因报告 |
| **修复** | 归因报告 | Prompt 调整 / 数据补充 / 检索策略优化 / 模型切换 | 修复方案 |
| **验证** | 修复方案 | 回归测试确认：(1) 目标问题修复 (2) 无退化 | 验证报告 |
| **沉淀** | 验证通过的 Case | 补充到 Golden Set + 更新评估维度 | 更新后的 Golden Set |

### PRD 中 Badcase 迭代要求模板

```
Badcase 管理要求：
1. 发现渠道：[线上采样/用户反馈入口/定期评估跑批]
2. 响应 SLA：P0（幻觉导致误导）[24h内修复]；P1（回答质量差）[本迭代内修复]
3. 归因分类：[幻觉/遗漏/格式错误/检索失败/推理错误/其他]
4. 回归要求：每次修复后需通过 Golden Set 全量回归，通过率不低于 [具体值]%
5. 沉淀要求：修复后的 Badcase 必须补入 Golden Set，并更新评估维度（如适用）
```

## 八、PRD 评估章节 Checklist

写 PRD 时用以下清单自查评估章节是否完整：

- [ ] L1-L2 指标已量化，含具体阈值和测量方式
- [ ] L3 业务指标已定义，含基线和目标值
- [ ] 评估框架已选定（RAGAS / DeepEval / 自定义）
- [ ] Golden Set 规模和分布已规划
- [ ] 三级评估执行频率已明确
- [ ] 回归测试与 CI/CD 集成要求已写入
- [ ] Badcase 闭环流程和响应 SLA 已定义
- [ ] 线上 Drift 监控采样策略已明确
